# Victory Sync Lead Gen Hub

## Meeting Booked and shared Supabase session

Apply the new migrations in order: `20261001_meeting_booked.sql`, `20261002_crm_role_claims.sql`, `20261003_call_booking_actor.sql`, then `20261004_company_meeting_booked.sql`. They add fields and triggers without changing existing lead rows. The CRM stores cold call, cold email, inbound, referral, import, and manual contacts in `public.leads`; `source` distinguishes them. Company prospects are a second pipeline in `public.companies` and now have a Meeting Booked stage and date picker too. `public.prospects` is the search staging table and links to a CRM lead through `lead_id` after import. `public.referrals` tracks affiliate commissions and accounts, rather than the CRM pipeline.

In the Supabase dashboard, open Vault and create two secrets. Use the Vault secret input so the webhook does not enter a committed file. The secret names are `victorysync_slack_meeting_webhook` and `victorysync_leadgen_origin`. The latter value is the HTTPS origin of this app, with no trailing slash, for example `https://app.victorysync.com`. The webhook must be an active Slack incoming webhook whose app is added to the destination channel. Do not use a Slack OAuth client secret for this webhook. `pg_net` queues delivery and the scheduled `victorysync-slack-response-check` job records Slack HTTP failures in `public.slack_notification_log`.

In Supabase Auth Hooks, select `public.crm_custom_access_token_hook` as the Custom Access Token Hook. Invite users through Team so each active `team_members` row has an `auth_user_id`, role, and any required client account. Refresh the session after a role change. Admin and owner can manage all CRM leads, agents can work on their assigned account or assigned leads, and clients can read only leads for their assigned account. Existing `member` and `viewer` roles remain supported. The client role requires a client account. Database RLS enforces direct lead access; the API also limits client reads and rejects client writes.

The VictorySync dashboard at `/victorysync` and Lead Gen Hub at `/leadgen` are routes in this one app. Both use `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` and the same Supabase browser client. The Lead Gen Hub card opens the existing session without an OTP handoff or second login. Sign out once to end the session for both routes. Keep `SUPABASE_URL` and `SUPABASE_ANON_KEY` pointed at the same project as the browser variables. No additional Auth redirect URL allow list entry is needed for this in-app navigation. Keep `SUPABASE_SERVICE_ROLE_KEY` server only.

To inspect the deployment, run [verify-meeting-booked.sql](scripts/verify-meeting-booked.sql) in the Supabase SQL editor. Its final transaction tests INSERT and UPDATE for each CRM source and rolls back all test leads and queued requests. Also test the Company CRM Meeting Booked stage in its editor. For an actual Slack delivery test, create a disposable lead in each source through the UI, book a future meeting, and inspect `slack_notification_log` after one minute. A `delivered` row and a `200` response confirm delivery. A `failed` row contains the HTTP status and response text. Also test admin, agent, and client accounts in the app, and attempt a direct Supabase lead query for a different client account to verify RLS.

The October 1 production audit found `pg_net` enabled and a legacy trigger named `trg_meeting_booked` attached only to `UPDATE OF status` on `public.leads`. Moving a lead to the existing `Meeting` pipeline stage did not change `status`; a booked call outcome existed as `disposition = 'meeting_booked'` while `status` stayed `new`. A rollback-only test that did change `status` failed with PostgreSQL error `42703` because the legacy function reads nonexistent `company_name` and `contact_name` columns. Its webhook is hardcoded in the function, and it lacks a fixed `search_path`. A direct webhook test returned Slack HTTP 200 with body `ok`, so the URL and channel installation worked at audit time. The replacement migration removes the old trigger and reads the webhook from Vault. Existing workforce RLS policies also restricted leads and pipelines to admins; the role migration replaces those policies with scoped Supabase JWT policies.

## Contacts data source
The Contacts UI uses the existing leads table. It contains the production contact records; crm_contacts is currently empty. The Vercel API applies pagination and filters before returning rows. Do not replace this source without migrating the data and preserving outreach references.

## Contact segments and smart lists

Apply `supabase/migrations/20261018_contact_segments.sql` before deploying the matching API and web app. It adds organization scoping to `segments`, backfills the two existing segments to VictorySync organization `cfbaf78a-3caa-4cb2-a367-d3b3eb161ba1`, adds static segment membership, and provides database functions for live counts, paginated filtering, bulk actions, call history, and last activity. The old `{ "source": "Other" }` and `{ "tags": ["top3-prospect"] }` filter formats are normalized on read. Existing outreach columns and sequence enrollments are preserved.

The Contacts list reads `leads` with server pagination, search, filters, and sorting. Column layout is stored in the browser. Named saved views use the existing `crm_saved_views` table with `object_type = 'contacts'`. Each segment has a shareable `/contacts/segments/:id` URL; counts are computed live and cached back to `segments.contact_count` when opened or edited. Static segments use `segment_contacts`, while smart segments re-evaluate their conditions.

`supabase/rollbacks/20261018_contact_segments.sql` reverses the migration. Export static segment membership before a rollback because that newly created join table is removed by the rollback.
